# Library API

REST API for library management developed with Java and Spring Boot.

This project is the evolution of my previous project, [library-manager](https://github.com/junior-2912/library-manager), originally developed in pure Java.

The main purpose of this project is to take the same library domain and rebuild it in a web environment, applying concepts such as Spring Boot, REST APIs, JPA, Hibernate, relational databases, DTOs, validation, exception handling and transaction management.

---

## About the project

Library API provides the main operations needed to manage:

- Books
- Users
- Book loans
- Loan history
- Overdue loans
- User and book rankings based on the loan history

The project started as a Java Core exercise in the [library-manager](https://github.com/junior-2912/library-manager) repository and was later migrated to Spring Boot to practice backend development and persistence with JPA/Hibernate.

The goal is not only to build a library system, but also to demonstrate the evolution from a Java-only application to a REST API backed by a relational database.

## Business Rules

The application currently applies the following business rules:

1. A book can only be borrowed when it is available.

2. A user can have a maximum of 5 active loans.

3. The loan date is generated by the application.

4. New loans always start with `ACTIVE` status.

5. A return date cannot be before the loan date.

6. A finished loan cannot be finished again.

7. Borrowed books cannot be deleted.

8. Users with active loans cannot be deleted.

9. Loans are not deleted because they represent the historical record of the system.

10. Rankings are based on the complete loan history, not only on active loans.

## Architecture

The project follows a layered architecture:

```text
HTTP Request
     |
     v
Controller
     |
     v
Service
     |
     v
Repository
     |
     v
Database
```
### Controller

Responsible for handling HTTP requests and returning HTTP responses.

### Service

Contains application logic and business rules.

This is where operations such as creating a loan, checking book availability and validating the user's active loan limit are performed.

### Repository

Responsible for persistence using Spring Data JPA.

### Entity

Represents the main domain objects and their relationships.

### Main entities:

- Book
- User
- Loan
- DTO

DTOs are used to control the data exchanged through the API.

For example, when creating a loan, the client sends:
```
{
  "userId": 1,
  "bookId": 1,
  "returnDate": "2026-09-10"
}
```
The client does not provide internal fields such as the loan ID, loan date or loan status.

### Exception Handling

Application exceptions are handled globally through @RestControllerAdvice, allowing business exceptions to be converted into standardized HTTP responses.

### Validation

Request DTOs use Jakarta Bean Validation together with @Valid to reject invalid input before it reaches the service layer.

### Database

The project currently uses H2 as an in-memory relational database.

This choice was intentional because the main purpose of the current version is to study and practice:

- Spring Boot
- JPA
- Hibernate
- ORM
- REST APIs
- Transactions
- Validation
- Exception handling

The application currently uses:

jdbc:h2:mem:librarydb

Since H2 runs in memory, the database is recreated when the application starts.

The H2 console can be used during development to inspect the database.

## API Endpoints
### Books

| Method | Endpoint | Description |
|---|---|---|
| GET | `/books` | List all books |
| GET | `/books/{id}` | Find a book by ID |
| POST | `/books` | Create a book |
| PUT | `/books/{id}` | Update a book |
| DELETE | `/books/{id}` | Delete a book |

### Users

| Method | Endpoint | Description |
|---|---|---|
| GET | `/users` | List all users |
| GET | `/users/{id}` | Find a user by ID |
| POST | `/users` | Create a user |
| PUT | `/users/{id}` | Update a user |
| DELETE | `/users/{id}` | Delete a user |

### Loans

| Method | Endpoint | Description |
|---|---|---|
| GET | `/loans` | List all loans |
| GET | `/loans/{id}` | Find a loan by ID |
| POST | `/loans` | Create a loan |
| PATCH | `/loans/{id}/finish` | Finish a loan |
| GET | `/loans/late` | List overdue books |
| GET | `/loans/users` | Rank users by total loans |
| GET | `/loans/books` | Rank books by total loans |

Loans do not have a delete endpoint because they represent historical records of the system.

Example: Create a Book
Request
```
POST /books
Content-Type: application/json
{
  "isbn": "9780132350884",
  "title": "Clean Code",
  "author": "Robert C. Martin"
}
Response
201 Created
```
The Location header points to the newly created resource.

Example: Create a Loan
Request
```
POST /loans
Content-Type: application/json
{
  "userId": 1,
  "bookId": 1,
  "returnDate": "2026-09-10"
}
```
The application automatically defines:

loanDate   → current date
loanStatus → ACTIVE

The client is responsible only for providing the user, book and expected return date.

### Error Handling

The API uses centralized exception handling with @RestControllerAdvice.

Some of the situations handled by the application include:

- Resource not found
- Book already borrowed
- Borrowed book cannot be deleted
- User has reached the active loan limit
- Loan has already been finished
- User cannot be deleted while it has active loans
- Invalid request data

Responses follow a standardized structure.

Example:
```
{
    "error": "Validation error",
    "errors": [
        {
            "field": "userId",
            "message": "não deve ser nulo"
        }
    ],
    "message": "Invalid fields",
    "path": "/loans",
    "status": 400,
    "timestamp": "2026-09-04T19:54:19.543040900Z"
}
```

Validation errors are handled separately and can identify the fields that failed validation.

### Validation

The API uses Jakarta Bean Validation in request DTOs.

For example:

@NotNull
private Long userId;

@NotNull
private Long bookId;

@NotNull
private LocalDate returnDate;

The controller uses:

@Valid

to trigger validation of incoming request bodies.

This separates basic request validation from business rules handled by the service layer.

### JPA and Hibernate

Persistence is implemented using Spring Data JPA and Hibernate. 

The project uses entity relationships such as:
```
Loan
 ├── User
 └── Book
```
The application uses JPA entities as the domain model and repositories based on JpaRepository.

Hibernate is responsible for translating the JPA mappings and operations into SQL executed against the database.

### Transactions

Loan operations use @Transactional where multiple changes must be treated as a single operation.

For example, creating a loan may involve:
```User
  ↓
increase active loans

Book
  ↓
change to BORROWED

Loan
  ↓
create ACTIVE loan
```
These changes should succeed together or be rolled back together.

#### Database-side reporting

The current reports are calculated in Java using Streams.

For example, the ranking logic currently follows the idea of:
```
findAll()
 ↓
Stream
 ↓
groupingBy()
 ↓
counting()
 ↓
sorting
 ↓
top 5
```
A future improvement is to move these aggregations to the database using JPA/JPQL and SQL concepts such as:

- GROUP BY
- COUNT
- ORDER BY
- LIMIT

The goal is to avoid loading all loan records into application memory when only aggregated results are needed.

The expected evolution is:

Current:
```
Database
   ↓
all loans
   ↓
Java
   ↓
Streams
   ↓
ranking
```

Future:
```
Database
   ↓
JPQL / SQL
   ↓
GROUP BY + COUNT + ORDER BY
   ↓
only required results
   ↓
Java
```
